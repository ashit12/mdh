mdh matching engine: an instrument registry and dense book slots (Stage 1)

The change
----------
MatchingEngine used to hold std::unordered_map<InstrumentId, MatchingBook>, and book_for()
was books_[instrument_id] -- a lazy insert. Instrument ids come from clients, so any id a
client invented got a book of its own, allocated on the spot, forever. That is the hole
this stage closes.

The engine now takes its universe at construction and rejects anything else:

  MatchingEngine(std::span<const InstrumentId> universe, std::size_t expected_resting_orders)

  slot_of_id_ : vector<uint32>, direct-mapped, sized to the largest id (capped at 1<<22,
                so 16 MB worst case). kNoSlot means unregistered -- the bounds check IS
                the validity check.
  books_      : vector<MatchingBook>, indexed by slot, dense.
  by_id_      : sorted (id, slot) pairs, so snapshot() no longer sorts on every call.

A command naming an unregistered instrument is rejected with RejectReason::InvalidInstrument,
checked ahead of every other field. RiskGatedEngine checks it before the risk check, because
risk would otherwise answer the wrong question: a sell on an instrument the exchange does
not trade came back InsufficientPosition, which reads as something a deposit would fix.

register_instrument() exists for replay, which means books_ can grow, which means every
MatchingBook in it moves. Outstanding handles survive that because a book's pool sits behind
a unique_ptr (stable address) and moving a pmr container with an equal allocator relinks
nodes rather than copying them. MatchingEngine.RegisteringAnInstrumentKeepsRestingOrdersReachable
rests an order, registers 63 more instruments, then cancels and fills through handles taken
before the moves.

The journal is now self-describing: a fourth frame type, RegisterInstrument (payload:
instrument_id), written once per instrument when the journal is opened, ahead of any command.
run_command_replay() registers from those frames as it reads them, so a replay reproduces the
run that wrote the file without being told the universe out of band. Readers that predate the
type reject it cleanly as InvalidMessageType rather than misparsing.

Correctness: all 395 tests pass (12 new), clean under ASan. The pipeline's concurrency test
now submits 20,000 registered instruments, which makes it a scale test of the registry too.

Expectation going in was 3-6% from replacing a hash, a bucket load and a node hop with a
bounds check and two array loads. That is roughly what the whole-engine numbers show; the
lookup-dominated microbenchmarks show more.

The FOK-rejected row with nothing crossable is the cleanest read on what this stage actually
did: that path is a lookup and an immediate answer, and it used to pay a hash miss
(crossable_quantity() called books_.find() and returned 0 when it missed). It is now a bounds
check and an array load, and the operation more than halved. Cancel at 4096 levels moving 36%
is larger than a lookup can explain on its own and is probably partly variance; the 65536-level
rows not moving at all fits -- at that depth the tree walk dominates everything else.


Memory (bench_matching_memory)
==============================================================================================
Unchanged, as expected: this stage moves a per-instrument container, not a per-order one.

  1,000,000 resting orders, 1 order/level:  345.9 bytes/order before and after
  1,000,000 resting orders, 100/level:      214.9 bytes/order before and after

Total allocations for a 1,000,000-order book: 815 before, 816 after -- one more, and 112 bytes
fewer overall. The engine trades one unordered_map's bucket array for three small vectors, and
at one instrument that is a rounding error. It stops being one at scale: the old map allocated
a node per instrument on first touch, from a client-supplied id, without limit.


Where this leaves things
------------------------
The nanoseconds are real but they are not why this stage exists. It exists because the engine
no longer allocates on client-controlled input, because replay no longer needs to be told what
the exchange traded, and because a tick ladder is sized instruments x band x 2 sides -- which
cannot be budgeted until the instrument set is bounded and known. Stage 2 (slab plus intrusive
FIFO levels) is next, and the cancel and sweep rows above are the ones it should move.
