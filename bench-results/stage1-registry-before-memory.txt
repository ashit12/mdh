mdh matching-engine baseline: allocation behaviour and memory footprint

=== Allocations per matching-engine operation =================================
Averages over a batch, so a fractional count is real (amortised container growth),
not a rounding artefact. "net bytes" is allocated minus freed: it is what the
operation leaves behind on the heap, and should be ~0 for anything that does not
grow the book.

=== Memory footprint of a resting book ========================================
Directly measured, not estimated: live bytes is (allocated - freed) across building
the book, using the platform allocator's own reported block sizes, so allocator
rounding is included. RSS delta is a coarse cross-check that includes page-level
granularity and the process's other state.

=== Which structures the bytes go to ==========================================
Allocation-size histogram for building a 1,000,000-order book (1 order per price
level, so every per-order structure is exercised once). Sizes are the allocator's
block sizes. MatchingBook draws its nodes from a pool, so individual nodes are no
longer visible here at all: what reaches the allocator is the handful of bulk chunks
the pool then carves them out of, which is why nearly all the bytes land in the
>=1024 row and the total allocation count is a few thousand rather than a few
million.

Type sizes on this build:
  sizeof(BookOrder)                  48  (what a price level actually holds)
  sizeof(ExchangeRestingOrder)       64  (the reassembled form: commands, snapshots)
  sizeof(Price)                       8
  sizeof(ExchangeOrderId)             8
  sizeof(std::pmr::list<BookOrder>)  32  (a price level's FIFO header)
