mdh matching engine: one order directory instead of two (Tier 4)

The change
----------
Every resting order used to live in two hash tables. MatchingEngine::live_orders_ mapped
(account_id, client_order_id) -> (instrument_id, exchange_order_id); MatchingBook::index_
then mapped that exchange_order_id -> Location. Cancel and replace paid both, strictly in
series: the second lookup could not start until the first returned. Every resting order
carried two hash nodes, in two tables that grew and rehashed independently.

They are now one table, owned by the engine:

  orders_ : (account_id, client_order_id) -> { book handle, original_quantity,
                                               order_sequence, instrument_id }

MatchingBook stops being an order directory and becomes only a book. It cannot find an
order by id and no longer knows its own instrument. add() returns an opaque Handle (side,
price, list iterator) and remove_at/reduce_at/set_client_order_id_at/at take it back. The
matching walk is unaffected: it works front-of-level and never needed a lookup.

What made this possible now is the Tier 3b split -- BookOrder carries account_id and
client_order_id, so a node found through the book can produce its own directory key. That
is what lets one table keyed by client identity serve the book's purposes too.

Behaviour is unchanged, deliberately including the awkward parts: the key is global rather
than per-instrument, so a client order id already live on a *different* instrument is still
a duplicate, and a cancel naming the wrong instrument is still UnknownOrderId.

Correctness: all 383 tests pass (three MatchingBook tests for unknown-id lookups no longer
have a subject and were dropped; one new test pins the handle-stability invariant the
scheme rests on). Clean under ASan, which matters more than usual here -- the engine now
holds list iterators across arbitrary other book traffic.

Reading it
----------
Cancel is the headline, which is what the design predicted: -19% to -56%, and BM_Cancel/65536
lands at 125 ns, better than the 131 ns it measured two tiers ago before Tier 3b's stride
change regressed it. Matching, sweeping and FOK execution all improve 12-26% -- not from
the lookup (they do none) but from the smaller, denser directory. Replace improves 10-25%
everywhere except the 65536-level cases, which are flat.

The one genuine regression is BM_Fok_Rejected_CrossableLevels/256, 1245 -> 1471 ns at a cv
of 0.3%. It is the same lone case that regressed in Tier 3b (+36% then, +18% now) while its
/64 and /1024 neighbours stay flat, which continues to look like cache-set aliasing at that
one level count rather than a cost that scales.

BM_Fok_Rejected_BackgroundDepth/0 printed +85% at a cv of 9.7% next to neighbours at cv 44%;
that block of the run was disturbed, not changed.

The per-order node count is unchanged in bytes -- one 128-byte block replaces two 64-byte
ones -- so the saving is the second table's bucket array, 8 bytes per order, plus the
allocator traffic of one fewer node.


What this exposed, and the second half of the change
----------------------------------------------------
At the extreme end the collapse on its own makes things worse, not better:

  1,024,000 resting orders, 1024 levels    1187 -> 1814 ns/op
  resting-only stream, sustained          156.4 -> 183.3 ns/op

Both are table-growth artefacts. One large table rehashes more expensively than two small
ones did, and at a million orders that dominates everything else.

So the directory is now sized rather than guessed. MatchingEngine takes an expected resting
order count (default 1024, unchanged behaviour for tests and small books) and reserves once;
MatchingPipelineOptions and OrderEntryGatewayOptions pass it through, so the two production
embedders can say what they expect. Getting it wrong is not a correctness problem, and
over-estimating costs 8 bytes per unused slot in exactly one array.

The reason this is worth doing now, when the same experiment was rejected two tiers ago, is
that the thing being sized has changed. Over-reserving used to mean a bucket array in every
MatchingBook -- 64 instruments, 64 arrays, and measurably worse p99 for the trouble. There
is now exactly one directory in the engine, so pre-sizing it is one allocation and one
policy decision, independent of how many instruments are trading.

bench_matching_workload now sizes each scenario's engine to what that scenario will actually
hold (workload.resting_orders_at_end, or the seeded depth), which is how a production engine
would be configured. Final numbers, against the Tier 3b build:
