mdh matching engine: hot/cold split of the resting order (Tier 3b, variant A)

The change
----------
The book no longer stores ExchangeRestingOrder. It stores BookOrder: the five fields
the matching loop reads per fill, plus the two enums that are free inside the same
48 bytes.

  BookOrder                48 bytes   exchange_order_id, client_order_id, account_id,
                                      price, remaining_quantity, side, time_in_force
  ExchangeRestingOrder     64 bytes   unchanged; still what commands, snapshots and
                                      hash_state_snapshot() are made of

Three fields left the order, chosen by tracing every read in the engine. instrument_id
is never read from a stored order at all -- the book is already selected by instrument
-- so MatchingBook now holds it once. original_quantity and order_sequence are read by
nothing except snapshot()/state hash, so they moved into the per-order index entry,
which had sixteen bytes of slack. all_bids()/all_asks() reassemble the whole order with
one index lookup each; find() and remove() reassemble it from data they already hold.
No runtime path pays an extra lookup.

Why 48 bytes and not smaller: a std::pmr::list node adds two links, and 48 + 16 is the
largest node the pool serves from a 64-byte block. Below 48 buys nothing, above 48
costs a doubling. The index entry has the mirror-image constraint at 40 bytes; both are
now guarded by static_asserts.

MatchingBook also gained a second pool. Once list nodes shrank to 64 bytes they shared
a size class with index nodes, which halved the density of both; separating them was
worth ~20% on mid-depth cancel under a matched filtered protocol.

Correctness: all 385 tests pass, including the replay-determinism state-hash tests and
MatchingBookStress, which compares whole reassembled orders against an independent
reference model.

untouched, which is why the 1-order-per-level shape improves by less in relative terms.
Allocation count rises from 1070 to 1094 for a million orders: the second pool asks
upstream for its own chunks.

Reading it
----------
Anything under 8% here is below the noise floor of this harness. Measured directly: the
same binary run twice in a row moves by a median of 3.0%, a p90 of 7.4%, and up to 38%
on BM_Cancel/4096. The rows worth reading are the large ones with a low cv on both
sides, and the two regressions below were each re-confirmed with five separate
processes per build under an identical filtered protocol.

Wins, all in the same direction and all explained by the smaller node:
  Resting onto an existing deep book        -10% to -22%
  Resting onto a new price level             -4% to -15%
  Replace (priority-losing) at 65536 levels        -17%
  Matching a 16-order level                         -9%

The two real regressions, both deep read-only walks:
  BM_Cancel/65536                        131 -> 157 ns   (+20%, cv 1.6/1.3)
  BM_Fok_Rejected_CrossableLevels/256    918 -> 1245 ns  (+36%, cv 0.1/0.3)

Both are level walks over a book far larger than L2, and both lost the same accident:
before the split, a list node (80 B) and a level's map node (72 B) both fell in the
128-byte size class, so a level's map node and its first order were allocated
consecutively out of the same chunk and usually landed within a line or two of each
other. At 64 bytes the list node moves to a different size class, so walking a level
now touches two separate memory streams instead of one. The second pool does not
address this -- it separates the index, not the levels -- and no pool configuration can:
sharing a class is precisely what created the adjacency, and re-creating it means
putting the list node back above 64 bytes.

BM_Cancel/65536 was already flagged as a regression by the previous tier (112 -> 131 ns)
with the note that Tier 3b would change the stride. It did, in the predicted direction.

Non-monotonic neighbours (FOK/64 +14%, FOK/256 +36%, FOK/1024 -9%) point to cache-set
aliasing at particular level counts on top of the stream effect, not to a cost that
grows with depth.
