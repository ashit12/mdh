mdh matching engine: ExchangeRestingOrder packed from 72 to 64 bytes

The change
----------
Two edits, which only work together:

  1. TimeInForce given an explicit uint8_t underlying type. Without one it defaults
     to int, four bytes for three enumerators.
  2. ExchangeRestingOrder's fields reordered widest-first.

Reordering on its own achieves nothing here -- verified by compiling it. Seven 8-byte
fields plus a 4-byte instrument id plus a 4-byte TimeInForce plus a 1-byte Side is 65
bytes of content, which rounds to 72 under 8-byte alignment in every permutation. Only
narrowing the enum brings the content to 62 bytes, and only then does ordering matter:

  current layout                              72 bytes
  reordered, TimeInForce left as int          72 bytes   (no gain)
  reordered, TimeInForce as uint8_t           64 bytes
  the above minus order_sequence and
    original_quantity (Tier 3b, not done)     48 bytes

Wire compatibility is unaffected: every encoder already writes TimeInForce as one byte
through an explicit static_cast<std::uint8_t>, and every decoder casts a uint8_t back.

C++20 requires designated initializers to appear in declaration order, so all four
construction sites were rewritten to match: two in matching_engine.cpp, one in
test_matching_book.cpp, one in test_matching_engine_stress.cpp.

What it does NOT do
-------------------
It does not reduce the book's memory footprint by a single byte, and this was expected
rather than discovered: MatchingBook draws list nodes from a pool that serves
power-of-two blocks, so a node holding a 64-byte order (80 bytes with its two links)
occupies the same 128-byte block as the 72-byte version (88 bytes) did. Confirmed by
measurement -- the footprint table and the allocation total (1070 allocations,
443441776 bytes for a 1,000,000-order book) are byte-for-byte identical to before.

Halving that block requires the payload at 48 bytes or less, which means removing
fields, not moving them.

Where it does show up: every copy of an order. all_bids()/all_asks() and the snapshots
built from them, plus the by-value returns from find() and remove(), all move 11% less
data.

Correctness: all 385 tests pass.

Reading it
----------
Cancel improves the most at shallow-to-middling depth (-4% to -7% for 1 through 4096),
which is the expected place for it: MatchingBook::remove() returns the order by value,
so it is a direct 8-byte-per-call saving. Matching and sweeping improve by 1-4%.

Two deep-book readings need care:

  BM_Rest_ExistingPriceLevel/65536 printed 185 ns at a cv of 42.8%, i.e. one repetition
  out of five was disturbed. Re-run with 9 repetitions it settles at 167 ns, cv 3.4%,
  against 170 ns before -- unchanged.

  BM_Cancel/65536 is a real and reproducible regression: 131 ns against 112 ns, and it
  holds at 131 ns with cv 1.2% over 9 repetitions. It is not explained by the struct
  size. That case holds 65,536 distinct price levels, roughly 8 MB of pool blocks
  against a 4 MB L2, so it is entirely cache-miss bound; and the block sizes did not
  change, so the access stride is identical to before. The likely cause is code or
  chunk alignment shifting under a different struct size rather than the size itself.
  Worth watching if Tier 3(b) follows, since that one does change the stride.
