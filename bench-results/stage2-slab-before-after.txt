mdh matching engine: a per-book slab and intrusive FIFO levels (Stage 2)

The change
----------
A price level used to be a std::pmr::list<BookOrder>: one pooled 64-byte node per resting
order, reached by pointer, plus a 32-byte list header living inside the price-index map node.
It is now a pair of indices into one flat per-book slab:

  struct SlabOrder { BookOrder order; uint32 next, prev; };   // 56 bytes, free list in `next`
  struct LevelSlot { uint32 head, tail; };                    // still std::map<Price, ...>

MatchingBook::Handle collapses from {side, price, list iterator} (24 bytes) to a single uint32
slot. The order knows its own side and price, so the handle no longer has to carry them. That
takes OrderRef from 48 bytes to 24, which takes the engine's directory node from 80 to 56.

std::map is deliberately retained as the price index. Isolating the slab from the ladder is
the whole point of splitting them into two stages: this file is what the slab did on its own.

Two things fall out of using indices rather than pointers. A handle now survives the slab
being relocated, so growth cannot invalidate one -- the list-iterator version needed the pool
to guarantee that. And a slot freed on one side can be reused by the other, since a slot
carries nothing of the level it came from.

Correctness: all 398 tests pass (3 new), including the 400,000-operation MatchingBookStress
comparison against an independent reference model, which is what actually exercises free-list
reuse and unlink-from-the-middle.

Sizing, and why it is here
--------------------------
The slab is a flat vector, so it grows by relocating. Left to grow on its own that costs a
copy of the whole slab -- amortised, but the amortisation is the problem: at a million resting
orders across a thousand levels, an insert measured 104 ns against a slab that grew into it,
versus 61 ns for the list it replaced. Every other row improved; that one did not.

MatchingEngine already takes expected_resting_orders and already sizes its directory from it,
and every benchmark and caller already passes an honest figure. The book was simply ignoring
it. Each book now reserves an equal share, and the row returns to 47 ns -- 24% faster than the
list rather than 69% slower. This is the same mechanism, the same failure mode, and the same
cure as the directory table's documented 81-vs-1814 ns, so it belongs with it rather than
being worked around structurally. The alternative -- chunked, never-relocating storage -- was
rejected because it adds an indirection to every slab access, including the sweep, which is
the path this stage most improves.

All numbers below are medians of 2-3 runs on an otherwise-loaded laptop. p50/p90/p99 are
reproducible to a few percent; p99.9 and max are not, and are marked where they appear.

The largest wins in the whole stage are here, which was not the prediction -- the slab was
supposed to pay for itself on insert and sweep, and a cancel is dominated by the tree walk.

likelier to hit. Stage 3 removes this walk entirely, so expect these rows to move again.

The gate was "bytes/order should fall by roughly 64". It fell by 138 at a million orders,
because three structures shrank rather than one: the order itself (a 64-byte pooled list node
became a 56-byte slab entry), the price-index node (72 bytes to 48, having shed the list
header), and the directory node (80 to 56, following the handle). The last two look like they
each crossed a pool size-class boundary, which would account for the drop being larger than
the arithmetic on the struct sizes alone suggests.

The rows that moved least are the ones where vector capacity slack is worst: a 100,000-order
slab sits in a 131,072-entry buffer (31% slack), where a 1,000,000-order slab sits in a
1,048,576-entry one (4.9%). Sizing the engine removes that too, and these figures are measured
with the default sizing on purpose, as the pessimistic case.

Allocations per operation are unchanged at zero for everything except a new resting order,
which is now 0.001-0.002 -- the amortised slab growth. Gross bytes/op for those rows went up
slightly (260 to 286) while net bytes/op went down (245 to 181): that is a relocation both
allocating and freeing, which the old pooled list never did.


Where this leaves things
------------------------
Every gate the plan set for stage 2 is met: allocations per order fell, bytes per order fell
by more than twice the predicted amount, and latency improved on 53 of 58 microbenchmarks and
every whole-engine figure. The mixed workload is 6.9% faster on top of stage 1's 13%.

The one surprise is where the wins landed. The sweep improved as designed (13% per level), but
the biggest single movement is cancel against a deep book (-48% at 4096 levels), which came
from shrinking the map node rather than from the slab itself. Stage 3 replaces that map with a
tick ladder, so those rows are about to be rewritten again -- worth noting that stage 3's
predicted gains were extrapolated from the *pre-slab* tree cost, and the tree is now cheaper
than it was, so the headroom stage 3 is aiming at is smaller than it looked.
