mdh matching engine, Tier 3(a): front_of_best() returns a pointer, not a copy

The change
----------
MatchingBook::front_of_best() returned std::optional<ExchangeRestingOrder> by value,
so match_and_rest() copied the whole 72-byte resting order (80 bytes with the optional's
engaged flag and padding) out of the book on every iteration of the matching loop, to
read five or six scalars from it. It now returns const ExchangeRestingOrder*, valid until
that side of the book is next mutated.

That lifetime caveat is the whole substance of the change. The loop emits BookOrderRemoved
*after* calling remove_front(), which destroys the order the pointer refers to, so the
fields still needed at that point (account, client order id, exchange order id, side,
price) are now read into locals before the book is touched. Under the old signature the
copy is what made that safe; the copy was, in effect, paying for five scalars.

Baseline for this comparison is the Tier 0 build (pmr node pooling + reserve), measured
in the same session as the after numbers.

Allocation behaviour: identical to Tier 0, as expected -- the copy was on the stack, so
removing it changes no allocation counts. Verified by re-running bench_matching_memory
and diffing the per-operation table (tier3a-after-memory.txt).

Correctness: all 385 tests pass, including the mixed-command-stream stress test that
checks every invariant against a reference model and the replay-determinism test.

What to read out of that table
------------------------------
The paths that actually run the matching loop improve by a couple of percent on average,
and the improvement grows with how many fills the operation does -- which is what you
would expect from removing a per-fill cost:

  17 matching-loop cases: mean change -2.2%, best -5.1%, worst +2.0%

  the single-fill cases (Match/1, Sweep/1, Fok_Executed/1) are flat to slightly noisy;
  the deep ones (Match/256 -5.1%, Sweep/256 -2.7%, Fok_Executed/1024 -2.2%) all improve.

This is the expected size of the effect. One 72-byte copy per fill is a handful of
cycles against everything else a fill does (a map lookup to find the best level, a list
node touch, two event constructions through a std::function sink), so removing it moves
the deep-sweep cases by a few percent rather than transforming them. It is worth having
because it is free at runtime and costs only the discipline of reading fields out before
mutating.

The two cases flagged as slower, BM_Replace_PriorityLosing_*/1, are the ones to be
careful about: their before figures carry cv of 12.0% and 12.9%, versus 1.7% and 1.6%
after. A ~10 ns difference between a very noisy measurement and a quiet one is not
evidence of a regression, and there is no mechanism for one -- on a non-crossing replace
the loop breaks before it reaches any of the changed code, having done strictly less
work than before (no copy at all).


Workload benchmark
==============================================================================================
The mixed-workload figure is too noisy at this effect size to say anything. Four runs,
the first of the Tier 0 build and the rest of the Tier 3(a) build:

  mixed (realistic 40/25/20/10/5), sustained ns/op
    Tier 0    :  151.1
    Tier 3(a) :  155.4, 145.1, 150.1, 151.3

A 7% band across runs of one unchanged binary swamps a 2-5% effect. (For the same
reason, the earlier Tier 0 run measured this at 158.8 and the pre-change run in this
session measured 144.2 -- identical code both times.)

The one workload number stable enough to read is the pure crossing stream, which is
nearly all matching loop and therefore where this change should show up:

  crossing (IOC, one fill each, one level), sustained ns/op
    Tier 0    :  39.3, 38.2
    Tier 3(a) :  37.6, 37.6, 37.1, 37.6

Around 2% faster, consistent with the microbenchmarks.


Conclusion
==============================================================================================
A small, real, no-cost win: 2-5% on every path that runs the matching loop, nothing
changed anywhere else, no allocation impact, no behaviour change. Tier 3(b) -- shrinking
ExchangeRestingOrder itself -- is the half of Tier 3 with the large effect still in it,
and is not simple: instrument_id and side are recoverable from the book, but
order_sequence and original_quantity are serialized into the persistence state hash
(src/exchange/persistence/state_hash.cpp) and compared by the snapshot tests, so removing
them from the stored order changes a durable contract rather than just a layout.
